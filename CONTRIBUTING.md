# Contributing to Vela

This guide is for people who want to **build, test, or contribute to the Vela framework itself**. If you
just want to *use* Vela to build Dataverse plugins and Custom APIs, see the [README](README.md) - you do
not need to clone this repository.

Looking for something to work on? See the [open issues](https://github.com/allandecastro/vela/issues) for planned and candidate work.

Taking part in this project means following the [Code of Conduct](CODE_OF_CONDUCT.md). Found a security
vulnerability? Do not open an issue: report it privately as described in [SECURITY.md](SECURITY.md).

A pull request runs `ci.yml` (and `docs.yml` / `mutation.yml` when it touches their paths) on GitHub-hosted Windows
runners, forks included, plus the [changelog check](#changelog); the [pull request template](.github/pull_request_template.md) lists what a change needs
before review.

## Solution layout

```text
Vela.sln
src/
  Vela.Plugins/     # Plugin runtime (net462): base types, step builder, contexts, DI, caching, Custom APIs
  Vela.Messages/    # Typed request/response base classes (net462 + net10.0), referenced by Vela.Plugins
  Vela.Analyzers/   # Roslyn analyzers VELA001-VELA028 and the image/step-context source generator (netstandard2.0)
  Vela.CodeFixes/   # IDE code fixes, packed inside Vela.Plugins with the analyzers
  Vela.Testing/     # Test harness (net462): in-memory Dataverse, PluginContext, PluginPipeline
  Vela.Cli/         # The vela tool (net10.0): plan/apply, init/add, models, sign, logs
tests/              # One test project per src project, plus package fixtures for the CLI scanner
docs/               # The docfx site; docs/samples holds the compiled snippets it includes
tools/
  codegen/Vela.StepApiGen/  # Generator for the step builder surface (maintainer tooling, never packed)
.github/workflows/  # ci.yml, mutation.yml, docs.yml, release.yml
```

AI coding agents: [`AGENTS.md`](AGENTS.md) summarises this guide.

### Generated code

`StepApi.cs`, `StepBuilder.Impl.cs` and `TypedTriggers.cs` in `src/Vela.Plugins/Steps/` are **generated** (they
carry an `<auto-generated>` header) from the message model in `tools/codegen/Vela.StepApiGen/MessageModel.cs`. Never
edit them by hand: change the model (one line per message) and regenerate, then commit the model and the three
outputs.

```bash
dotnet run --project tools/codegen/Vela.StepApiGen              # rewrite the generated files
dotnet run --project tools/codegen/Vela.StepApiGen -- --check   # exit 1 if they are stale (what CI runs)
```

See [Add a typed plugin message](docs/contributing/extending-plugins.md) for the hand-written files a new message
also touches.

## Architecture rules

Follow these rules when you add code (see [Architecture](docs/advanced/architecture.md#architecture-rules)):

1. **`Vela.Plugins` is the runtime.** It holds framework code, contracts, primitives and immutable definitions, and
   runs in the Dataverse sandbox.
2. **`Vela.Cli` is the tooling.** It is the one CLI used locally and in CI.
3. **Early-bound models belong to the consumer.** Generated model code lives in the plugin repository, not in this
   one.
4. **No sample application code in the shipped packages.** Samples and fixtures live under `docs/samples` and
   `tests`.
5. **Registration metadata and runtime execution stay separate.** They meet only through `StepDefinition`.

## Build and test

```bash
dotnet build Vela.sln -c Release
dotnet test Vela.sln -c Release      # Windows
```

The runtime, harness and their tests target `net462`. `dotnet build` works on every OS, but `dotnet test` runs a
`net462` test project only on Windows. On macOS and Linux, run the `net10.0` projects (`Vela.Cli.Tests`,
`Vela.Analyzers.Tests`, `Vela.CodeFixes.Tests`) with `dotnet test`, and the `net462` ones (`Vela.Tests`,
`Vela.Testing.Tests`, `docs/samples/Vela.DocSamples`) with Mono and the xUnit console runner:

```bash
mono ~/.nuget/packages/xunit.runner.console/2.9.2/tools/net462/xunit.console.exe \
  tests/Vela.Tests/bin/Release/net462/Vela.Tests.dll tests/Vela.Testing.Tests/bin/Release/net462/Vela.Testing.Tests.dll \
  docs/samples/Vela.DocSamples/bin/Release/net462/Vela.DocSamples.dll
```

The console runner is not a dependency of any project: fetch the `xunit.runner.console` package once (for
example `nuget install xunit.runner.console -Version 2.9.2`) and adjust the path to where it lands.

### Test stack and coverage

The test project uses:

1. `xUnit` for unit tests
2. `Moq` for mocks
3. `Microsoft.NET.Test.Sdk` for `dotnet test`
4. `coverlet.collector` for code coverage

Run coverage (Cobertura) with:

```powershell
dotnet test .\tests\Vela.Tests\Vela.Tests.csproj `
  -c Release `
  --collect:"XPlat Code Coverage"
```

CI enforces a **branch-coverage gate** (via `coverlet.msbuild`) on five areas: the **diff engine** (plan/apply
idempotence), the **in-memory harness**, the **plugin runtime** (`Vela.Plugins`), the **analyzers** and the **code
fixes**. The run fails if branch coverage drops below the threshold. CI runs each test project once and collects
its coverage on that same run (the plugin runtime merges the `Vela.Tests` and `Vela.Testing.Tests` runs); a new
`*.Tests` project must be added to `ci.yml`, or the job fails. A gated test project must reference
`coverlet.msbuild`, otherwise the threshold is silently ignored. Reproduce a gate locally, e.g. the diff engine:

```bash
dotnet test tests/Vela.Cli.Tests/Vela.Cli.Tests.csproj -c Release \
  -p:CollectCoverage=true -p:ThresholdType=branch -p:ThresholdStat=total -p:Threshold=90 \
  -p:Include="[Vela.Cli]Vela.Cli.DiffEngine%2c[Vela.Cli]Vela.Cli.DefinitionNormalizer"
```

Thresholds are set just below current coverage to catch regressions without churn; raise them as coverage improves.

### Quality gates

Two gate families guard the correctness-critical cores, and both follow the same policy:

- **Branch coverage** (`ci.yml`) - diff engine, in-memory harness, plugin runtime (`Vela.Plugins`), analyzers and
  code fixes.
- **Mutation score** (`mutation.yml`, Stryker.NET) - the diff engine + normalizer, the harness query core and
  security model, the CLI apply / Custom API / reader / steps / scanner / role-generation cores, the analyzers and
  the plugin runtime (steps, context, DI / caching / localization). Weekly on every file; on a pull request, on the
  files it changes (`--since:main`, 80 floor). Each area's configuration is `tests/stryker/<area>.yml` (see
  [Mutation testing](docs/advanced/mutation-testing.md) for the per-core scores).

**Policy - 80% floor, ratcheted above it.** Every gated core stays at **≥ 80%** on *both* metrics; `80` is a hard
minimum, never to be lowered below. On top of that floor the enforced threshold is **ratcheted to just under the
current measured value** (≈2 pts), so it catches regressions without flaking - and is tightened as the score rises.
Branch coverage is the easier metric (currently ~85-92%); mutation score is stricter (a surviving mutant means a
test passed even though the code was broken), so it sits lower (~80% harness, ~90% diff engine). Treat the gate as
a *regression detector*, not a target to write tests for: if a run dips under the floor, **kill a surviving
mutant** (or add the missing test) to lift the score rather than relaxing the gate.

The tools tests include an **opt-in build smoke test** (`Generate_ThenDotnetBuild_Succeeds`) that packs
`Vela.Plugins`, scaffolds a solution via `vela init`, and runs `dotnet build` on it - the only test that
actually compiles the generated C#. It always runs in CI; locally it is reported as skipped unless enabled
(it restores/builds, so it needs the SDK and the Microsoft packages):

```powershell
# The smoke test packs Vela.Plugins / Vela.Testing / Vela.Messages as 1.0.0: evict any stale 1.0.0 from the
# global NuGet cache first, or it shadows the fresh local feed and the build compiles against old binaries.
foreach ($p in 'vela.plugins', 'vela.testing', 'vela.messages') { Remove-Item -Recurse -Force -ErrorAction SilentlyContinue "$env:USERPROFILE\.nuget\packages\$p\1.0.0" }
$env:VELA_BUILD_SMOKE = "1"
dotnet test .\tests\Vela.Cli.Tests --filter Generate_ThenDotnetBuild_Succeeds
```

## Changelog

Every user-visible change gets **one entry** in [`CHANGELOG.md`](CHANGELOG.md) under `## [Unreleased]`: framework
API or behaviour, CLI behaviour or output, analyzers, docs pages. Put it under the existing heading of its kind and
line, in this order: `Changed (Framework, breaking)`, `Added (Framework)`, `Changed (Framework)`, `Fixed (Framework)`,
`Changed (CLI, breaking)`, `Added (CLI)`, `Changed (CLI)`, `Fixed (CLI)`, `Docs`. CI, tests, internal refactors and
dependencies that aren't shipped need no entry; a change to a shipped dependency floor (e.g. `Newtonsoft.Json` in
`Vela.Plugins`) does.

The `Changelog` workflow fails a pull request that changes `src/` or `docs/` without touching `CHANGELOG.md`. When
no entry is needed, a maintainer adds the `no-changelog` label, which re-runs the check. Releases are cut by the
maintainer (see [RELEASING.md](RELEASING.md)): don't bump versions or move entries out of `## [Unreleased]`.

## Release

Release artifacts are produced by the release pipeline and should include only the framework packages
(`Vela.Messages`, `Vela.Plugins`, `Vela.Testing`) and the shared CLI tool (`Vela.Cli`).

The packages follow [Semantic Versioning](https://semver.org/) and ship as two independent release lines: the
**framework** (`Vela.Messages` + `Vela.Plugins` + `Vela.Testing`, versioned together) and the **CLI** (`Vela.Cli`). Record every
notable change in [`CHANGELOG.md`](CHANGELOG.md) under **Unreleased** as you merge it (see [Changelog](#changelog)); cutting a release means
renaming that section (with a date) and pushing the line's tag - `framework-vX.Y.Z` or `cli-vX.Y.Z` - which
packs and publishes only that line. See the changelog's *Versioning policy* section for the pre-1.0 rules.
