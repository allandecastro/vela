# Client-side: form scripts and web resources (preview)

> [!WARNING]
> **Work in progress.** Web resource support (the `--web-resources` scaffold, the TypeScript models, the
> `vela-client` runtime and `--webresources` deployment) is an incomplete preview. Anything on this page can change
> or be removed in any release; don't rely on it for production.

Vela's client-side support lets you author **model-driven form scripts** in TypeScript against typed,
generated form models, build them into a single bundle, and deploy them (and any static web resources) to
Dataverse. The CLI only automates the Dataverse-facing steps (generate, deploy); the build is plain `tsup`.

## The loop

```text
vela init --web-resources         # 1. scaffold the {prefix}.WebResources project (once)
vela models --forms --tables --out src/generated --overwrite   # 2. generate form models + table types + barrel
vela add form-script <entity>     # 3. scaffold + register a form script for a table (repeat per form)
# 4. fill in the form script against the model, in your editor
npm run build                     # 5. bundle with tsup (not the CLI)
vela apply --webresources <dist> --solution <name>  # 6. deploy the bundle + static assets, published
```

Each form web resource is one entry in `web-resources.entries.ts` (`<prefix>_/js/<entity>/Forms/main` -> its
`src/<entity>/Forms/main.ts` source). `tsup.config.ts` imports that map, and `vela add form-script <entity>`
maintains it, so you never edit the tsup config by hand. `add form-script` refuses to overwrite an existing file
(use `--force`); its entry-map insertion stays idempotent.

## 1. Scaffold the web resources project

`vela init --web-resources` adds an opt-in `{prefix}.WebResources` TypeScript project next to the plugin
projects (see [Scaffold a solution](scaffold.md)):

```powershell
vela init --name ZavaSales --prefix Zava --web-resources --web-resources-namespace zava
```

It emits `package.json` (tsup + Vitest, depends on `vela-client`), `tsconfig.json`, `tsup.config.ts`
(`globalName` = your publisher prefix; it imports the entry map from `web-resources.entries.ts`), a `.esproj` so
Visual Studio "Build" runs npm, and the `src/generated` (regenerated) vs `src` (hand-written) split. It ships a
**working** `account` example (form script + `fakeForm` test) with a small example model set under
`src/generated/`, so `npm install && npm test` are green out of the box; `vela models` then overwrites
`src/generated/` with the real models.

## 2. Generate the typed form models

`vela models --forms` reads your tables' published Main / Quick Create forms and emits one
`forms/<entity>/<form>.form.ts` per form (each `satisfies FormModel`) plus a shared `option-sets/` folder at the
output root, into `src/generated/` (see [Early-bound models](models.md)):

```powershell
vela models --forms --solution ZavaSales --out src/Zava.WebResources/src/generated --interactive
```

The model carries only the fields, tabs, sections and subgrids actually on that form, each typed by the same
rules as the C# early-bound models (string/memo, the numeric family, boolean, date, choice/multichoice, lookup
with its targets, guid, file, image). Scope by `--solution` (only that solution's tables) and/or `--entities`.

For **typed Web API queries** inside a form script, also generate the table record types with
`vela models --tables` (see [Early-bound models](models.md)): one `tables/<logicalname>.ts` per table,
each an `interface` plus a `defineTable(...)` descriptor the `createWebApi()` query layer consumes. **Combine
both scopes in one run** so a single `option-sets/` folder and one `index.ts` barrel cover everything (the
`@generated` alias imports form models, table types and enums from that one barrel):

```powershell
vela models --forms --tables --solution ZavaSales --out src/Zava.WebResources/src/generated --overwrite --interactive
```

> [!IMPORTANT]
> Each generated file starts with `// Generated by "vela models --forms --lang ts" - do not edit by hand.`
> Treat `src/generated/` as **regenerated, never hand-edited**: when a form changes, re-run the command into the
> same folder **with `--overwrite`** (the scaffold already ships example files there, so the first regeneration
> needs it) and commit the result. Editing a model by hand puts it out of sync with Dataverse. The output is
> deterministic, so re-running with no change produces no diff.

## 3. Write form scripts, 4. build

Extend `VelaForm(<model>)` with a class, use the typed field/tab accessors, and export the handlers with
`defineForm`. This is exactly what the scaffolded `account` example ships. Generated symbols come through the
`@generated` alias (a tsconfig path to `src/generated`, resolved by tsup and Vitest too), which points at the
generated [root barrel](models.md) - so one import line covers the form model, table types and enums:

```ts
// src/account/Forms/main.ts
import { VelaForm, defineForm, type SaveEventArgs } from 'vela-client';
import { createWebApi } from 'vela-client/webapi';
import { AccountMain, Contact, account_customertypecode } from '@generated';

export class AccountForm extends VelaForm(AccountMain) {
  onLoad(): void {
    this.fields.customertypecode.addOnChange(this.applyRules);
    this.applyRules();
  }

  applyRules(): void {
    const isCompetitor =
      this.fields.customertypecode.getValue() === account_customertypecode.Competitor;
    this.tabs.details.setVisible(!isCompetitor);
    this.fields.industrycode.setRequiredLevel(isCompetitor ? 'none' : 'required');
  }

  // Typed Web API query: the Contact ref infers the row type, and the polymorphic lookup target is typed too.
  async relatedContacts(): Promise<Array<{ name: string | null; parentType: string | null }>> {
    if (!this.id) return [];
    const { entities } = await createWebApi()
      .retrieveMultiple(Contact)
      .select('fullname', '_parentcustomerid_value')
      .filter((f) => f.eqGuid('_parentcustomerid_value', this.id))
      .execute();

    return entities.map((c) => ({
      name: c.fullname ?? null,
      parentType: c['_parentcustomerid_value@Microsoft.Dynamics.CRM.lookuplogicalname'] ?? null,
    }));
  }

  onSave(e: SaveEventArgs): void {
    if (!this.fields.name.getValue()) {
      e.preventDefault();
      this.setFormNotification('Account name is required', 'ERROR');
    }
  }
}

// `namespace` exposes the handlers at <prefix>.Forms.account.onLoad / onSave (aligned with the ribbon's
// <prefix>.Ribbon.<entity>.<command>), never "Vela". The onLoad/onSave exports are kept for the entries guard.
export const { onLoad, onSave } = defineForm(AccountMain, AccountForm, { namespace: 'zava.Forms.account' });
```

Then bundle with tsup (`npm run build`, or `npm run dev` to watch). The build is plain tsup, not the CLI.
The scaffolded project also includes Vitest; form scripts are unit-testable off-browser with the
`vela-client/testing` `fakeForm` harness, no live Dataverse. The example test shows **both layers** - the form
rules, and a form method that calls `createWebApi()`, tested with a fake ambient Web API via `fakeForm({ webApi })`:

```ts
// src/account/Forms/main.test.ts
import { describe, it, expect } from 'vitest';
import { fakeForm, createFakeWebApi } from 'vela-client/testing';
import { AccountMain, account_customertypecode } from '@generated';
import { AccountForm } from './main';

describe('AccountForm', () => {
  // Layer 1: form rules, driven with the fakeForm accessors.
  it('hides Details and relaxes industry for a competitor', async () => {
    const form = fakeForm(AccountMain, AccountForm);
    await form.load();
    form.fields.customertypecode.setValue(account_customertypecode.Competitor);
    form.fields.customertypecode.fireOnChange();
    expect(form.tabs.details.getVisible()).toBe(false);
    expect(form.fields.industrycode.getRequiredLevel()).toBe('none');
  });

  it('blocks save when the account name is empty', async () => {
    const form = fakeForm(AccountMain, AccountForm);
    await form.load();
    expect((await form.triggerSave()).prevented).toBe(true);
  });

  // Layer 2: a method that calls createWebApi(), tested with a fake ambient Xrm.WebApi.
  it('reads related contacts through the typed Web API', async () => {
    const accountId = '11111111-1111-1111-1111-111111111111';
    const api = createFakeWebApi();
    await api.createRecord('contact', { fullname: 'Ada Byron', _parentcustomerid_value: accountId });

    // recordId makes this.id non-empty; webApi installs the fake ambient for the form's lifetime.
    const form = fakeForm(AccountMain, AccountForm, { recordId: accountId, webApi: api });
    const rows = await form.instance.relatedContacts();

    expect(rows.map((r) => r.name)).toContain('Ada Byron');
    form.restore();
  });
});
```

Add more form scripts with `vela add form-script <entity>`, which scaffolds `src/<entity>/Forms/main.ts` (+ a
co-located test) and registers its entry.

## 5. Deploy the web resources

`vela plan` / `apply --webresources <folder> --solution <name>` mirror the build output folder to Dataverse
(see [Plan & Apply](plan-apply.md)):

```powershell
vela plan  --webresources src/Zava.WebResources/dist --solution ZavaSales --interactive
vela apply --webresources src/Zava.WebResources/dist --solution ZavaSales --interactive
```

The folder is mirrored **verbatim**: each file's unique name is its path relative to the root, so the
top-level folder (for example `zava_`) is a real folder, not a prepended prefix. The type is inferred from the
extension, a content hash drives the diff, and changed/created resources are published in one call. Reconciliation
is **additive and scoped to the top-level folders you deploy** (mirroring a subset folder never prunes another
team's folders), and each name must start with the solution's publisher prefix. `--webresources` requires
`--solution`, and needs no `--package` (you can deploy web resources on their own).

## Ribbon commands

Ribbon (command bar) buttons run **commands**: an **action** (runs on click) and, optionally, an **enable rule**
(a synchronous boolean deciding whether the button is enabled). You author each as a plain function taking the
typed command context and wire it with `formCommand` / `formRule`; `bootstrapCommands` attaches the wired set to a
dotted global the platform can call. The typed context is the generated `<Entity>Cmd` alias (a
`FormCommandContext` over the entity's Main form model), re-exported from `@generated` next to the model.

Scaffold a command module with `vela add ribbon-script <entity>` (creates `src/<entity>/Ribbon/commands.ts` + a
co-located test, and registers the entry). It reads the entity's generated Main form model from `@generated`, so
run `vela models --forms --entities <entity>` first:

```ts
// src/account/Ribbon/commands.ts
import { formCommand, formRule, bootstrapCommands } from 'vela-client/ribbon';
import { AccountMain } from '@generated';
import type { AccountCmd } from '@generated';

function reviewAccount(form: AccountCmd): void {
  form.tabs.details.setVisible(true); // typed accessors, like a form script
}

function canReview(form: AccountCmd): boolean {
  return Boolean(form.fields.name.getValue()); // enable rule: a synchronous boolean
}

export const commands = bootstrapCommands(
  { reviewAccount: formCommand(AccountMain, reviewAccount), canReview: formRule(AccountMain, canReview) },
  { namespace: 'Zava.Ribbon.account' }, // <Prefix>.Ribbon.<entity>
);
```

Test them off-browser with `fakeFormCommand` (form commands) / `fakeGridCommand` (grid / homepage commands):

```ts
// src/account/Ribbon/commands.test.ts
import { describe, it, expect } from 'vitest';
import { fakeFormCommand } from 'vela-client/testing';
import { AccountMain } from '@generated';
import { commands } from './commands';

describe('account ribbon commands', () => {
  it('enables the command once the account has a name', () => {
    const form = fakeFormCommand(AccountMain);
    expect(commands.canReview(form.primaryControl)).toBe(false);
    form.fields.name.setValue('Zava');
    expect(commands.canReview(form.primaryControl)).toBe(true);
    form.restore();
  });
});
```

**Deploy is maker-wired.** A command bundles to a web resource like a form script, so
`vela apply --webresources <folder>` already deploys it. The CLI does **not** generate a `RibbonDiffXml` / app
action: you add the button in the **Power Apps Command Designer** (its label, icon and location), and point its
action (and, if any, its enable rule) at the dotted global - `<Prefix>.Ribbon.<entity>.<command>`, for example
`Zava.Ribbon.account.reviewAccount`. That is exactly the `namespace` in `bootstrapCommands` plus the command name.

## Keeping models in sync

When a form changes, re-run `vela models --forms --tables --overwrite` into `src/generated/`, rebuild, and commit.
Never patch a generated model by hand.

## Machine-readable output

`vela models --json` (and `init` / `sign` / `add`) print a JSON report of what was generated or done, for
scripts and agents driving the CLI.
