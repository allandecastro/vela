# Authentication

The `vela` CLI talks to a live Dataverse environment for the commands that read or
write registration state - `plan`, `apply` and [`vela models`](../guides/models.md).
All of these share the **same connection flags**, so once you know how to authenticate
one, you know how to authenticate them all.

There are four ways to connect:

- the **ambient Azure credential** (just `--url` - uses your `az login` or a managed identity, no browser),
- a full **connection string**,
- **client id / client secret** (an app registration),
- **interactive browser login** (a wizard, for local use).

## Connection options

| Option | Flags | When to use |
| --- | --- | --- |
| Ambient credential | `--url` (only) | The simplest, headless default: local `az login` or a managed identity / workload identity in CI. |
| Connection string | `--connection-string` | You already have a Dataverse connection string. |
| Client id / secret | `--url` + `--tenant-id` + `--client-id` + `--client-secret` | Unattended automation / CI with an app registration. |
| Interactive | `--interactive` | Local use - signs in through the browser with a wizard. |

## Ambient Azure credential (recommended)

When you pass **only** `--url` (no connection string, no client-secret flags, no `--interactive`), Vela acquires
a Dataverse token from the ambient Azure credential chain (`Azure.Identity` `DefaultAzureCredential`) - no
browser and no extra flag:

```bash
# Uses your existing 'az login' locally, or a managed identity / workload identity in CI
az login   # once, if you are not already signed in
vela plan --package ./artifacts/Zava.Plugins.1.0.0.nupkg --url https://zava.crm.dynamics.com --solution Zava
vela apply --package ./artifacts/Zava.Plugins.1.0.0.nupkg --url https://zava.crm.dynamics.com --solution Zava --auto-approve
```

The credential chain covers environment variables, workload identity / managed identity (CI and Azure-hosted
runners), and a local `az login` session, so the same command works on a developer machine and in a pipeline.
Any explicit method below (`--connection-string`, client-secret flags, or `--interactive`) takes precedence when
provided.

## Client id / client secret

For unattended runs, authenticate with an app registration by passing the environment
URL, tenant, application (client) id and a client secret:

```powershell
# Compare local package(s) with live Dataverse state (client id / client secret)
vela plan `
  --package .\artifacts\Zava.Plugins.1.0.0.nupkg `
  --url https://zava.crm.dynamics.com `
  --tenant-id <tenant-id> `
  --client-id <app-id> `
  --client-secret <client-secret>
```

The secret can be supplied three ways:

| Method | How | Notes |
| --- | --- | --- |
| Environment variable | `DATAVERSE_CLIENT_SECRET` | Preferred. Nothing on the command line. |
| Standard input | `--client-secret-stdin` | Preferred. Pipe the secret in. |
| Flag | `--client-secret <client-secret>` | Discouraged - visible to shell history and process listings; the CLI warns when you use it. |

> [!WARNING]
> `--client-secret` is exposed to shell history and process listings (the CLI warns
> when you use it). Reach for the environment variable or `--client-secret-stdin`
> instead. See [Environments & CI](environments-secrets.md) for the CI patterns.

## Interactive browser login

For local work, run any of the connected commands with `--interactive` to sign in
through the browser with a wizard - no flags or secrets required:

```powershell
vela plan --interactive
```

The first `--interactive` run opens the browser; the token is then **cached across runs**, so later runs sign in
silently. The cache is a file under the Vela config dir (`~/.vela`, or `$VELA_CONFIG_DIR`): DPAPI-encrypted on
Windows and a user-only file on macOS/Linux. Pass `--fresh-login` to force a new browser prompt, or run
[`vela logout`](../reference/cli-cheatsheet.md) to clear the cached token and the remembered Dataverse URL.

The scaffolded solution also includes a `Zava.ConsoleApp` project: a .NET 10 console
app that signs in to Dataverse interactively (browser). It is generated by
[`vela init`](../guides/scaffold.md) unless you pass `--no-console`.

## Sovereign clouds and custom app registrations

For sovereign clouds or custom app registrations under `--interactive`, override the
MSAL login with:

| Flag | Purpose |
| --- | --- |
| `--auth-client-id` | The client id used for the interactive MSAL login. |
| `--authority` | The authority (login) endpoint to sign in against. |

## Connection timeout

Every connected command talks to Dataverse with a default request timeout of **10 minutes**. On a very large
environment, or on the first run after a deploy while the plugin sandbox cold-starts, a single request can take
longer than the default; raise it with `--timeout <minutes>`:

| Flag | Purpose |
| --- | --- |
| `--timeout <minutes>` | Dataverse request timeout in minutes (default 10, range 1 to 60). Raise it for a large org or a slow cold start. |

```bash
vela apply --package ./artifacts/Zava.Plugins.1.0.0.nupkg `
  --url https://zava.crm.dynamics.com --solution Zava --auto-approve --timeout 20
```

For running unattended in CI, including `--strict` and `--verbose`, see
[Environments & CI](environments-secrets.md).
